Finger Lickin Music

Complete Product Requirements and Technical Specification

Document purpose: Define the complete game, its functionality, user experience, technical architecture, data models, performance requirements, testing strategy, and implementation sequence for an agentic AI software development agent.

Implementation status: Specification only. Do not implement the game while preparing or reviewing this document.

Primary platform: Desktop browsers and mobile browsers.

Deployment constraint: The complete game must be deliverable as one standalone HTML file containing its HTML, CSS, JavaScript, UI, gameplay systems, and embedded resources where practical. External dependencies must be avoided unless they provide substantial functionality that would be impractical to reproduce reliably.

2. Product Vision

Finger Lickin Music is a browser-based 3D music creation, instrument-playing, rhythm, dance, and multiplayer game.

It combines the accessibility of a four-button rhythm game with the musical flexibility of an instrument simulator, a multitrack recording workstation, a MIDI playback environment, and a customizable 3D virtual band.

Players must be able to:

* Play instruments using four primary buttons.
* Perform notes, intervals, chords, riffs, and rhythmic patterns.
* Play freely without predefined notes.
* Record performances and layer multiple instruments into complete tracks.
* Compose using musical keys, scales, tempo, time signatures, and other musical settings.
* Import existing musical arrangements and play along with them.
* Visualize performances through animated 3D musicians whose movements correspond to actual musical events.
* Play using a dance mode inspired by dance rhythm games.
* Customize the appearance of band members and avatars.
* Play alone, locally where supported, or with other players online.
* Use the game on desktop and mobile devices.
* Save, load, and export projects using supported formats.
* Run the application from a single HTML file with minimal external dependencies.

The product must feel like a game first while offering meaningful musical capabilities rather than merely simulating musical interaction.

3. Product Principles

3.1 Musical accuracy

Musical events, instrument assignments, note pitches, velocities, timing, articulation where available, and polyphonic arrangements must be preserved as accurately as the source data and playback engine allow.

3.2 Playability

A beginner must be able to produce satisfying music with four buttons, while advanced users can access chords, alternate voicings, free play, and more precise controls.

3.3 Visual responsiveness

The 3D performance must communicate which instruments are playing, which notes are being performed, the intensity of the performance, and the musical structure.

3.4 Accessibility across devices

Desktop keyboard and controller inputs and mobile touch inputs must offer equivalent access to the core game.

3.5 Faithful import

Imported arrangements must retain their musical structure. The game must not silently simplify polyphonic or multitrack music into an inaccurate monophonic representation.

3.6 Honest technical limits

The application must distinguish between a format that is fully supported, partially supported, imported through a conversion path, or unsupported.

3.7 Single-file delivery

The primary deliverable is one HTML document. If an optional service is necessary for functionality such as online multiplayer, it must be clearly separated from the standalone core and documented.

5. Platform and Deployment Requirements

5.1 Supported environments

The application must target modern versions of:

* Desktop Chromium-based browsers.
* Desktop Firefox.
* Desktop Safari.
* Mobile Safari on iOS.
* Mobile Chromium-based browsers on Android.

Compatibility must be established through testing rather than assumed from browser names alone.

5.2 Standalone operation

The game must be designed to run when the user opens the HTML file directly, subject to browser security restrictions.

The agent must verify the actual behavior of local-file execution in supported browsers.

Core gameplay, the UI, local audio playback, basic visualization, and local project functionality must not require a remote server.

5.3 Single-file packaging

The final HTML should contain:

* Application markup.
* Styling.
* Application logic.
* Core game systems.
* Musical timing and mapping logic.
* Audio synthesis and playback logic.
* Rendering logic.
* Built-in presets and configuration.
* Embedded resources where feasible.

External libraries may be included in the file if their licensing and size permit it. Alternatively, a dependency may be loaded remotely only if the resulting limitation is clearly documented.

The primary artifact must not require a separate build pipeline or a collection of JavaScript files to function.

5.4 Required distinction: standalone versus online

The application must expose two operating contexts:

1. Standalone mode: no server required; local gameplay and local projects.
2. Online mode: optional network services for multiplayer and any explicitly network-dependent features.

A single HTML file cannot independently provide a persistent, authoritative, publicly reachable multiplayer server. Online multiplayer therefore requires an external service or server unless a suitable existing infrastructure is provided.

The standalone application must remain usable when that service is unavailable.

7. Core Gameplay Modes

7.1 Quick Play

Quick Play provides the shortest path from launch to performing music.

The player selects:

* A built-in song or imported arrangement.
* A playable instrument or dance mode.
* Difficulty.
* Control layout.
* Optional backing tracks.
* Performance visualization.
* Audio and input settings.

The game must transition from song selection to active play without requiring access to the studio.

7.2 Instrument Rhythm Mode

The player performs a selected instrument by pressing four primary buttons in time with incoming musical events.

The mode must support:

* Single notes.
* Multiple simultaneous notes.
* Chords.
* Intervals.
* Repeated-note patterns.
* Sustained notes.
* Rests.
* Rhythmic subdivisions.
* Tempo changes where supported by the arrangement.
* Multiple difficulty levels.
* Optional automatic accompaniment.
* Scoring and performance feedback.

The gameplay mapping must be instrument-independent at the input layer while allowing instrument-specific musical mappings.

7.3 Free Play

Free Play removes the requirement to follow a predefined song.

Players must be able to:

* Trigger notes and chords.
* Select an instrument.
* Select a musical key.
* Select a scale or chromatic mode.
* Adjust the playable register.
* Adjust octave.
* Control note duration.
* Control velocity or intensity where supported.
* Enable sustain.
* Use a metronome.
* Adjust tempo.
* Record and replay a performance.
* Switch between musical layouts.
* Disable scale constraints for unrestricted playing.

The mode must distinguish between quantized and unquantized playing.

7.4 Studio Mode

Studio Mode is a lightweight multitrack music creation environment.

It must provide:

* Track creation.
* Instrument assignment per track.
* Recording.
* Playback.
* Overdubbing.
* Track mute and solo.
* Volume and pan.
* Track naming.
* Tempo and time-signature configuration.
* Musical key and scale settings.
* Basic track positioning and timing edits.
* Looping and section playback.
* Undo and redo for supported operations.
* Save, load, and export.
* A basic mixer.
* A clear distinction between MIDI-event editing and audio rendering.

Studio Mode is not required to reproduce every feature of a professional digital audio workstation, but its core recording and playback operations must work reliably.

7.5 Imported Song Mode

Imported songs must be playable as rhythm-game experiences.

The user must be able to:

* Import a supported music file.
* Inspect the detected tracks and instruments.
* Select the track or tracks to play.
* Choose the target instrument.
* Map imported notes to the four-button layout.
* Select difficulty or automatic mapping.
* Play along with the source arrangement.
* Mute or lower the target instrument.
* Slow down or speed up playback.
* Seek to a musical position.
* Loop a section.
* Pause and resume without timing drift.
* View the score and performance feedback.
* View the virtual band performing the arrangement.

The source arrangement must remain intact internally even when the playable part is simplified for four-button controls.

7.6 Dance Mode

Dance Mode provides a rhythm-game experience based on dance steps rather than instrument performance.

It must support:

* Four directional or position-based step inputs.
* Keyboard and touch controls.
* Optional controller input.
* Step charts aligned to musical time.
* Multiple difficulty levels.
* Timing judgments.
* Combos and score.
* Miss and accuracy feedback.
* Song progress.
* Optional avatar choreography.
* Configurable input layouts.
* Custom or imported dance charts where supported.

The dance chart system must be independent of instrument note mapping.

7.7 Multiplayer

Multiplayer must support:

* Room creation and joining.
* A room code or equivalent join mechanism.
* Player identity and avatar.
* Song and mode selection.
* Ready states.
* Host-controlled session settings.
* Synchronized start and pause behavior.
* Shared tempo and song position.
* Per-player performance state.
* Multiplayer scoring.
* Reconnection handling.
* Graceful handling of a disconnected host.
* Session cleanup.

The product must distinguish between:

* Shared-song synchronized play.
* Cooperative performance.
* Competitive scoring.
* Shared creative sessions.

Features that cannot be completed reliably in the initial multiplayer release must be explicitly scoped and documented.

8. Four-Button Input and Musical Mapping

8.1 Input abstraction

All physical and virtual inputs must feed a shared input abstraction.

Supported sources should include:

* Keyboard.
* Mouse where applicable.
* Touchscreen.
* Standard game controllers where available.
* Optional MIDI input devices where browser support permits.

Every source must normalize into consistent press, release, hold, and timestamp events.

8.2 Default controls

A proposed desktop layout is four adjacent keys, such as A, S, K, and L.

The exact keys must be configurable.

Mobile must expose four large touch controls. The controls must support simultaneous presses where the browser and device allow them.

8.3 Mapping profiles

The system must support multiple profiles.

Profile A: Four-note lane mapping

Each button represents a lane or note group. Simultaneous buttons create chords.

Profile B: Interval mapping

The buttons represent musical intervals relative to a selected root.

Profile C: Chord mapping

The buttons represent selected chord types or voicings, with configurable root selection.

Profile D: Scale mapping

The buttons trigger notes selected from a scale, with configurable octave and register.

Profile E: Instrument-specific mapping

Mappings are adapted to the selected instrument and its playable range.

Profile F: Rhythm mapping

The buttons represent rhythmic or percussive actions.

The user must be able to switch profiles without modifying the source arrangement.

8.4 Chord and polyphony behavior

The input system must support:

* Simultaneous button presses.
* Multiple active notes.
* Note-on and note-off events.
* Held notes.
* Sustained notes.
* Repeated notes.
* Chord recognition where relevant.
* Instrument-specific note limitations where necessary.

Polyphonic source material must not be discarded because the player uses four buttons.

8.5 Input calibration

The user must be able to configure:

* Input offset.
* Audio output latency compensation.
* Visual lead time.
* Touch-control behavior.
* Hold and release behavior.
* Note sustain handling.

The implementation must avoid applying latency compensation twice.

9. Rhythm Engine and Scoring

9.1 Musical event timeline

The rhythm engine must operate on a musical timeline based on ticks or another precisely defined representation.

It must support:

* Tempo.
* Time signature.
* Tick resolution.
* Beat and subdivision positions.
* Note-on and note-off events.
* Chords.
* Tempo maps.
* Time-signature changes where available.
* Song position.
* Loop regions.
* Count-in.
* Pause and resume.
* Seeking.
* Playback speed changes.

Musical time must be kept separate from rendering frame time.

9.2 Scheduling

Audio playback and visual gameplay must share a common timing model.

The audio scheduler must schedule events ahead of playback using the audio clock. The rendering loop must estimate the corresponding musical position without using frame count as the authoritative clock.

Background-tab throttling and dropped rendering frames must not permanently shift the musical timeline.

9.3 Judgments

The game must define configurable timing windows for judgments such as:

* Perfect.
* Great.
* Good.
* Miss.

The exact thresholds must be configurable by difficulty and documented in milliseconds.

A judgment must compare the input timestamp against the intended event timestamp after applying the configured calibration.

9.4 Scoring

The scoring system must support:

* Per-note judgments.
* Combo.
* Maximum combo.
* Accuracy percentage.
* Score.
* Miss count.
* Song completion percentage.
* Per-player statistics in multiplayer.

Scoring must be deterministic for equivalent input event sequences.

The game must not score visual frame timing as though it were actual musical timing.

11. Audio Engine

11.1 General requirements

The audio engine must provide reliable playback for:

* Synthesized notes.
* Sampled instrument sounds.
* Percussion.
* Polyphonic sequences.
* Multitrack arrangements.
* Live input.
* Recorded performances.
* Imported MIDI.
* Metronome clicks.
* Backing tracks.

The audio engine must support independent track volume and mute state.

11.2 Audio implementation

The preferred browser-native foundation is the Web Audio API.

The agent must evaluate:

* Oscillator-based synthesis.
* Sample-based playback.
* General MIDI sound-bank playback.
* Sound-bank size and loading time.
* Polyphony limits.
* Voice allocation.
* Note stealing.
* Envelope handling.
* Audio scheduling.
* Mixing and master output.

The implementation must use a suitable combination of synthesis and samples rather than assuming that simple oscillators can reproduce every instrument convincingly.

11.3 General MIDI fidelity

The target is broad General MIDI program coverage, including melodic instruments and percussion.

The specification must distinguish:

1. Correct instrument program assignment.
2. Correct note pitches and timing.
3. Correct percussion channel and drum mapping.
4. Reasonable timbral similarity.
5. Accurate instrument articulations and expression.

These are different fidelity levels.

General MIDI is a sound assignment standard, not a guarantee of identical sound across synthesizers.

The game should provide General MIDI program mapping and, where licensing and file size permit, a compatible embedded sound bank or an explicitly documented alternative.

If the entire sound bank is too large for the practical standalone file budget, use a documented strategy such as optional sound-bank loading or a reduced built-in sound set. Do not claim full acoustic fidelity when using simplified synthesis.

11.4 Instrument behavior

Instrument playback must preserve available event information, including:

* Pitch.
* Velocity.
* Duration.
* Program selection.
* Channel.
* Sustain.
* Pitch bend.
* Modulation.
* Volume and expression.
* Pan.
* Relevant controller changes.

Unsupported controllers must be handled deterministically and documented.

11.5 Audio recording

The application must distinguish between:

* MIDI-event recording.
* Recording of the player’s input events.
* Recording the rendered audio output.
* Exporting a final mixed track.

MIDI recording preserves editable musical events. Audio recording preserves the rendered sound.

Browser support and user-gesture requirements must be considered when capturing audio.

11.6 Audio performance

The engine must avoid:

* Blocking the main UI thread during playback.
* Unbounded voice creation.
* Uncontrolled memory growth.
* Large synchronous audio decoding tasks.
* Scheduling every event only when it becomes visually visible.

The agent must define and test polyphony and track-count limits for target devices.

12. 3D Rendering and Performance Visualization

12.1 Stage

The stage must provide a real-time 3D environment with:

* Camera control.
* Lighting.
* Ground or stage geometry.
* Optional environmental elements.
* Musicians and instruments.
* Visual effects.
* Performance-reactive elements.

The user must be able to select from at least several camera perspectives, including a full-band view and a focused musician view.

12.2 Humanoid avatars

Musicians must use a skeletal or equivalent articulated character representation capable of animating:

* Torso.
* Head.
* Neck.
* Shoulders.
* Upper and lower arms.
* Hands or hand targets.
* Hips.
* Upper and lower legs.
* Feet.

A practical implementation may use procedural skeletons rather than complex imported character models.

Each avatar must support a consistent rig interface so that different instruments and character appearances can share the animation system.

12.3 Instrument performance animation

Animation must correspond to actual musical events rather than generic looping movements alone.

Examples:

* Piano and keyboard: hand movements correlated with notes and chord density.
* Guitar and bass: fretting-hand positioning and strumming or picking activity.
* Drums: limb motion coordinated with drum and cymbal events.
* Strings: bow or plucking motion where supported.
* Winds and brass: instrument-specific hand and breath-related gestures.
* Percussion: strikes aligned to percussion events.
* Synthesizers: keyboard performance or control gestures.

The system must not imply that every instrument can be animated with the same generic arm movement.

12.4 Abstract visualization

Some instruments or source events may not have a practical one-to-one humanoid animation.

The game must support abstract visual representations, including:

* Floating notes.
* Pitch or frequency indicators.
* Animated shapes.
* Particles.
* Rings or waves.
* Instrument-specific visual motifs.
* Motion trails.
* Beat-synchronized stage effects.

Abstract visualizations must preserve the relationship between the underlying event and its visual representation.

12.5 Polyphonic visualization

The visualization must support multiple simultaneous notes and multiple performers.

Animation intensity may be driven by note density, velocity, rhythmic activity, or other measurable musical attributes.

It must not require a separate humanoid character for every MIDI note.

12.6 Rendering architecture

The agent must compare an appropriate lightweight 3D approach against a custom WebGL implementation.

A library may be justified if it significantly reduces implementation complexity and is compatible with the standalone HTML requirement.

The architecture must define:

* Scene graph.
* Camera system.
* Geometry and material management.
* Avatar rig.
* Animation mixer or procedural animation scheduler.
* Event-to-animation mapping.
* Lighting.
* Asset loading.
* Resource disposal.
* Render scaling.
* Quality settings.
* Device capability detection.

12.7 Performance fallback

When full rendering is too expensive, the game must degrade gracefully.

Possible fallback levels:

1. Full 3D stage and skeletal animation.
2. Reduced 3D geometry and lighting.
3. Reduced animation complexity.
4. Simplified stage with abstract instrument visualizations.
5. Lightweight non-3D visualization where necessary.

Audio and musical timing must take priority over decorative rendering.

15. File Import and Export

15.1 Import architecture

All supported formats must pass through a common internal music representation.

The import pipeline must:

1. Validate the input.
2. Identify the file format.
3. Parse the source.
4. Normalize tracks and musical events.
5. Preserve supported metadata.
6. Report unsupported features.
7. Present the imported tracks for inspection.
8. Make the arrangement available to playback, visualization, and gameplay systems.

15.2 MIDI

MIDI support must include Standard MIDI Files where supported by the chosen parser.

The parser must handle:

* Format 0.
* Format 1.
* Track events.
* Delta times.
* Tempo maps.
* Time signatures.
* Key signatures.
* Program changes.
* Note-on and note-off.
* Velocity.
* Controllers.
* Pitch bend.
* Sustain pedal.
* Track names and metadata where available.
* Percussion channels.
* Simultaneous notes.

Running status, variable-length quantities, end-of-track events, and other structural details must be handled correctly.

Malformed or truncated files must not crash the application.

15.3 MusicXML

MusicXML import must preserve supported information such as:

* Parts and instruments.
* Measures.
* Notes and rests.
* Durations.
* Chords.
* Ties.
* Time signatures.
* Key signatures.
* Tempo markings.
* Articulation and dynamics where available.
* Repeats and navigation markings where supported.

The agent must explicitly define support for compressed MusicXML containers and uncompressed XML variants.

Engraving and complete notation rendering are separate features from event import and must not be assumed merely because MusicXML can be parsed.

15.4 Guitar Pro

The agent must identify the specific Guitar Pro versions and file extensions supported by the selected parser.

Guitar Pro compatibility must be implemented through a verified parser or a clearly documented conversion path.

The implementation must not claim universal support for all Guitar Pro versions.

Where imported data includes tablature-specific information, preserve supported information such as:

* String and fret.
* Tuning.
* Capo.
* Rhythmic duration.
* Bends.
* Slides.
* Hammer-ons and pull-offs.
* Palm muting.
* Harmonics.
* Track and instrument information.

Unsupported notation features must be reported rather than silently discarded.

15.5 Additional formats

The architecture should permit future adapters for formats such as:

* WAV.
* MP3.
* OGG.
* FLAC where browser decoding permits.
* Other sequencer or notation formats through verified adapters.

Finger Lickin Music — Edge Cases and Critical Failure Modes
This document extends the existing specification. Add it as a mandatory section of the agentic AI implementation plan, and include every subsection in the end-to-end table of contents generated before implementation begins.
1. Highest-impact risks
These issues should be addressed before adding large amounts of gameplay content.
Priority	Risk	Potential impact
Critical	Audio timing drifts away from gameplay	Rhythm scoring becomes unreliable
Critical	Audio is blocked by the browser	Game appears broken or silent
Critical	MIDI parsing loses or misorders events	Imported music plays incorrectly
Critical	Note-off events are lost	Instruments sustain indefinitely or produce stuck notes
Critical	Rendering blocks audio scheduling	Audio glitches during complex 3D scenes
Critical	Single-file constraint is misunderstood	Final application depends on missing assets or services
Critical	Multiplayer relies on message arrival time	Players hear or see events at different times
Critical	Saving fails or corrupts projects	Users lose recorded music
High	Mobile touch events remain stuck	Continuous notes, missed inputs, or incorrect scores
High	Polyphonic playback exceeds resource limits	Crashes, dropped notes, or audio distortion
High	File-format compatibility is overstated	Users cannot open files advertised as supported
High	Project state leaks between modes	Incorrect instruments, tempo, or tracks after switching
High	Browser storage assumptions are incorrect	Projects disappear or cannot be saved
High	Imported data is treated as trusted	Excessive resource consumption or security vulnerabilities
Browser behavior is a particularly important risk: audible playback can be blocked until user interaction, and Web MIDI device access is not available consistently across browsers. These must be handled as explicit capability and recovery cases, not assumptions.
2. Audio engine and musical timing edge cases
These are the highest-priority correctness requirements because the audio engine is shared by rhythm gameplay, free play, recording, song playback, and multiplayer.
2.1 Audio lifecycle
The agent must handle all of the following:
* The browser blocks audio before the first user gesture.
* The audio context becomes suspended while the game is running.
* The user switches tabs and returns after several minutes.
* The device locks its screen or enters a power-saving state.
* The user connects or disconnects headphones during playback.
* The operating system changes the default audio output device.
* A sample fails to decode or is unavailable.
* The user repeatedly starts and stops songs.
* Audio initialization is attempted more than once.
* A recording is started before audio initialization completes.
Required behavior: Audio state must be explicitly managed. Failed playback must produce a recoverable error or a clear resume action. Reinitialization must not create duplicate audio engines or overlapping playback.
2.2 Timing and scheduling
* A rendering frame takes 100–500 ms to complete.
* The browser throttles animation in a background tab.
* A tempo change occurs during playback.
* The song contains multiple tempo changes.
* The player pauses during a sustained note.
* The player seeks while notes are active.
* A loop boundary occurs during a sustained note.
* The user changes playback speed while playing.
* The audio clock and performance clock diverge.
* A scheduled event falls exactly on a loop boundary.
* Several notes share an identical timestamp.
* A dense chord contains many simultaneous note events.
Required behavior: Audio scheduling must use the audio clock rather than frame count. Pause, seek, looping, and tempo changes must have explicit rules for active notes and future scheduled events.
2.3 Stuck notes and voice management
* A note-on event has no matching note-off event.
* A note-off arrives before its note-on event.
* The same pitch is triggered repeatedly before release.
* Two overlapping notes use the same pitch and MIDI channel.
* A sustain pedal is pressed and never released.
* A track ends while notes are active.
* A program change occurs while notes are sustaining.
* The maximum polyphony limit is reached.
* A user changes instruments while holding a note.
Required behavior: Provide deterministic voice cleanup, note-release handling, sustain-pedal recovery, and a global panic/stop operation. The operation must stop active voices without leaving notes or audio nodes running indefinitely.
3. MIDI and music-file edge cases
File parsing must be treated as a data-integrity problem, not simply as an import dialog.
3.1 MIDI structural cases
* Format 0 file containing all events on one track.
* Format 1 file containing multiple synchronized tracks.
* Format 2 file containing independent sequences.
* Missing or invalid header.
* Invalid track length.
* Truncated variable-length quantity.
* Invalid event status byte.
* Missing end-of-track event.
* Duplicate or conflicting metadata.
* Running-status events.
* Empty track.
* Track containing metadata but no notes.
* File with extremely large event counts.
* File containing zero-duration notes.
* File containing unmatched note-on and note-off events.
* Note-on with velocity zero used as note-off.
* Multiple simultaneous notes with identical pitches.
* Events sharing timestamps but appearing in different tracks.
* Unusual ticks-per-quarter-note values.
* SMPTE-based timing instead of musical ticks-per-quarter-note timing.
Required behavior: Validate the header and event boundaries, enforce resource limits, preserve valid event ordering, and report malformed data. Do not interpret every MIDI file as a single synchronized song without checking its format.
3.2 Musical interpretation cases
* Tempo is not explicitly defined.
* Tempo changes occur multiple times.
* Time signature changes mid-song.
* Key signature changes mid-song.
* A track contains multiple program changes.
* Percussion is assigned through a designated channel.
* Pitch bend or modulation changes during a note.
* Sustain pedal changes note duration.
* Notes extend across measures.
* A file uses unusual note velocities.
* A note falls outside the playable instrument’s range.
* Several instruments use the same MIDI channel.
* Track names are missing or duplicated.
* The final event occurs after the last note has ended.
Required behavior: Preserve the original event data separately from normalized gameplay data. Missing metadata must use documented defaults, not guessed values presented as source facts.
3.3 MusicXML and Guitar Pro cases
* Compressed MusicXML is imported instead of uncompressed XML.
* The file contains multiple parts, voices, or staves.
* Chords and tied notes cross measure boundaries.
* Tuplets and unusual rhythmic subdivisions occur.
* Repeats and alternate endings are present.
* A score uses transposing instruments.
* Guitar tablature uses alternate tuning or a capo.
* A Guitar Pro file contains unsupported effects.
* The file was created by a version not supported by the parser.
* An import converts notation to MIDI and loses notation-specific information.
* The file is valid but contains no playable events.
Required behavior: Publish a precise compatibility matrix identifying supported versions and preserved features. Do not silently flatten unsupported notation, discard instrument-specific information, or claim universal Guitar Pro compatibility.
3.4 Imported audio files
* Unsupported codec.
* Corrupted audio.
* Very long audio file.
* Very large decoded audio buffer.
* Variable bitrate audio.
* Audio containing silence at the beginning.
* Audio containing a long fade-out.
* Audio file without tempo or beat metadata.
* Audio and MIDI files have different start offsets.
Required behavior: Audio playback and MIDI event playback must use a defined synchronization offset. Do not assume that arbitrary audio can be converted into accurate note charts without a transcription system.
4. Four-button input and scoring edge cases
4.1 Input handling
* Two, three, or four buttons are pressed simultaneously.
* A button is held while another is pressed.
* A key is released after the window loses focus.
* The user holds a key through a pause.
* The operating system intercepts a keyboard shortcut.
* Two players use the same keyboard.
* Touch input produces duplicate pointer and touch events.
* A touch ends outside the original button.
* A finger is dragged from one button to another.
* The user rapidly alternates between buttons.
* Key repeat fires while a key is held.
* The input device disconnects mid-performance.
* Input calibration is changed during a song.
Required behavior: Each physical press must produce a predictable logical press/release lifecycle. The implementation must suppress duplicate events and recover held inputs on focus loss, cancellation, pause, or device disconnection.
4.2 Scoring and mapping
* Two target notes occur at the same timestamp.
* A chord overlaps another chord.
* A target event is missed and later retried.
* An input falls exactly on a judgment-window boundary.
* An input is received before the visual target appears.
* The player presses a button when no note is expected.
* A note is sustained across a scoring boundary.
* A chart has more simultaneous notes than four buttons can represent.
* A scale mapping excludes a source note.
* Two source notes map to the same button.
* The difficulty changes during chart preparation.
* The player changes instrument during an active song.
Required behavior: Define deterministic rules for simultaneous notes, ambiguous mappings, missed events, held notes, and unsupported chords. Never silently delete source notes to make a chart fit four buttons.
The full source arrangement must remain available even when a particular gameplay mapping is lossy.
5. Studio, recording, and project persistence
5.1 Recording
* Recording starts before the count-in finishes.
* Recording starts while playback is already running.
* Recording stops while notes are held.
* The user records over an existing take.
* Two tracks record simultaneously.
* The browser suspends audio during recording.
* The user changes tempo during a recording.
* The recording contains many simultaneous notes.
* The recording exceeds the available memory.
* The user navigates away before saving.
Required behavior: Recording must define a consistent time origin, track assignment, and note-release policy. Interrupted recording must not corrupt previously saved takes.
5.2 Editing and mixing
* A user deletes a track referenced by an active recording.
* A track is muted while a note is sustaining.
* A track is soloed while another track is already soloed.
* Multiple tracks produce clipping.
* Volume or pan is changed during playback.
* Undo is invoked repeatedly.
* Redo is invoked after a new edit.
* A track is moved beyond the song’s current end.
* Quantization would move a note across a measure boundary.
* A track uses an instrument unavailable in the current sound bank.
Required behavior: Editing operations must maintain valid project state. Undo and redo must restore both musical events and associated track configuration where applicable.
5.3 Saving and loading
* Storage quota is exceeded.
* A write is interrupted.
* The browser closes during a save.
* A project contains missing audio references.
* A project uses an older schema version.
* A project contains unknown fields.
* A project is partially corrupted.
* The same project is opened twice.
* Two browser tabs edit the same project.
* A saved project is renamed or moved.
* The user attempts to overwrite a project with a smaller or incomplete version.
* The project includes large recordings or embedded assets.
Required behavior: Use validated, versioned project serialization and safe replacement strategies. Do not assume that browser storage is permanent or unlimited. Provide explicit export and recovery paths.
6. 3D visualization and avatar edge cases
6.1 Animation accuracy
* Many notes trigger simultaneously.
* A musician changes instruments mid-song.
* A track contains long rests.
* Notes are extremely short.
* Notes sustain for several measures.
* The camera switches while animation is active.
* A musician is hidden or moved offstage.
* The source instrument has no matching humanoid rig.
* The avatar’s instrument attachment point is missing.
* A character customization option changes body proportions.
* The animation system receives events out of order.
* The renderer drops several frames.
Required behavior: Animation must be derived from musical state and event timestamps, not from the number of frames rendered. Abstract visualization must remain available when an instrument-specific humanoid animation is unavailable.
6.2 Rendering and resources
* WebGL initialization fails.
* GPU resources are exhausted.
* The device cannot sustain the target frame rate.
* The browser loses its graphics context.
* A model or texture fails to load.
* A large scene causes excessive memory consumption.
* A user repeatedly switches scenes.
* A character is customized during playback.
* Mobile orientation changes during a performance.
Required behavior: Release unused resources, support reduced rendering quality, and provide a fallback visualization. A graphics failure must not permanently corrupt the audio timeline or the saved project.
7. Dance mode edge cases
* Two dance steps occur simultaneously.
* A hold begins before a pause and ends after resume.
* The chart contains an unsupported step type.
* A song’s tempo changes during a dance sequence.
* The user changes difficulty after chart generation.
* A touch remains active while the page is interrupted.
* The choreography asset is unavailable.
* The chart and audio have different starting offsets.
* A chart has overlapping or contradictory steps.
* A player misses several consecutive steps.
Required behavior: Dance charts must use the shared musical timeline. Missing choreography must not disable dance scoring or step input. Chart validation must reject or explicitly resolve contradictory events.
8. Multiplayer edge cases
Multiplayer is a separate distributed system and must have its own tests and operational requirements.
8.1 Session management
* Two users join simultaneously.
* A room is full.
* An invalid room code is entered.
* The host leaves before the song starts.
* The host disconnects during a song.
* A player joins after the start.
* A player reconnects with stale state.
* The same player joins twice.
* A room expires while a player is reconnecting.
* The server restarts during a session.
8.2 Synchronization
* Network latency increases sharply.
* Packets arrive out of order.
* Duplicate input messages arrive.
* A player has a substantially different clock offset.
* A pause message arrives after a resume message.
* A late message refers to an old song position.
* Players use different rendering frame rates.
* Players load different versions of the same chart.
* One player has a different audio output latency.
* The host changes tempo or seeks during a session.
Required behavior: Define server authority, session versioning, clock-offset estimation, message ordering, duplicate suppression, and late-event handling. Never use message arrival time as the sole authority for musical timing.
8.3 Security and abuse
* A client submits impossible scores.
* A client sends malformed messages.
* A client floods the room with inputs.
* A client attempts to join a private room without authorization.
* A client sends an oversized avatar or project payload.
* A player changes their local clock to manipulate results.
* A client sends events for a song that is not active.
* A room receives repeated reconnection attempts.
Required behavior: Validate session state and payloads, apply rate limits, and define which scores are authoritative. The client must not contain private server credentials.
9. Single-HTML-file and browser edge cases
These cases directly test the deployment constraint.
* The HTML is opened using a file:// URL.
* The application is served over HTTP or HTTPS.
* An external dependency is unavailable.
* The browser is offline on first launch.
* A CDN blocks or changes a dependency.
* An external resource is incompatible with the current browser.
* The HTML file exceeds practical download or memory limits.
* Embedded resources cause excessive startup time.
* The browser refuses access to a local file.
* A feature requires a secure context.
* A feature requires a server-side permission or response header.
* Browser storage behaves differently under local-file execution.
* A file import is blocked by a browser restriction.
* A mobile browser suspends the page.
* The browser does not support a required graphics feature.
Required behavior: Test the actual distributed HTML in each claimed environment. Clearly distinguish core standalone functionality from features requiring HTTPS, permissions, external resources, or server infrastructure.
The Web MIDI API is not universally available and requires a secure context in supporting browsers, so physical MIDI-device integration must remain optional rather than being a prerequisite for four-button gameplay.
10. Common architecture mistakes to prohibit
The agent must explicitly guard against these implementation failures:
1. One global state object for everything. Audio, gameplay, editing, and multiplayer state become coupled, causing mode transitions to break unrelated systems.
2. Using rendering time as musical time. Frame drops create timing errors and inaccurate scores.
3. Treating MIDI as audio. MIDI describes musical events; it requires a synthesizer or instrument to produce sound.
4. Treating every instrument as monophonic. Chords and overlapping notes are lost.
5. Using generic animations for every instrument. The visualization no longer reflects actual performance.
6. Assuming four buttons can represent every source arrangement without information loss. Mapping must be explicit and configurable.
7. Using browser storage as the only backup. Users can lose work due to quotas, clearing data, or browser behavior.
8. Building multiplayer before defining the timeline protocol. Retrofitting synchronization later causes expensive redesign.
9. Loading all assets at startup. Large sound banks and 3D assets can delay or prevent first play.
10. Adding dependencies without a packaging strategy. The final HTML may fail when opened offline or directly from disk.
11. Claiming full format support after testing only one sample. Compatibility requires a representative corpus and documented version coverage.
12. Marking UI completion as feature completion. Every feature requires functional tests.
13. Ignoring cleanup on mode transitions. Active notes, timers, animation loops, listeners, and network connections can accumulate.
14. Silently degrading fidelity. When a sound bank, effect, or animation is unavailable, the limitation must be visible and documented.
15. Implementing every subsystem before testing any subsystem. Incremental validation is required to prevent interacting defects from becoming difficult to isolate.
11. Mandatory failure-recovery rules
Every subsystem must define the following before implementation:
* What can fail.
* How the failure is detected.
* What state remains valid.
* Whether the operation can be retried.
* Whether user data is at risk.
* How the user is informed.
* Whether the application can continue in degraded mode.
* How the system returns to a known-good state.
* Which automated test verifies recovery.
The minimum recovery rules are:
* Audio failure must not destroy project data.
* Rendering failure must not permanently stop the musical transport.
* File-import failure must not corrupt the current project.
* Save failure must not falsely report success.
* Network failure must not disable standalone gameplay.
* Invalid input must not crash the application.
* Interrupted recording must not overwrite the previous successful take.
* An unrecoverable mode transition must return to a valid application state.
12. Required additions to the pre-implementation table of contents
The agent must add these dedicated sections to the original roadmap, before writing code:
* Risk register and severity classification.
* Audio lifecycle and recovery matrix.
* Timing, scheduling, and drift test plan.
* MIDI parser edge-case corpus.
* MusicXML and Guitar Pro compatibility matrix.
* Input lifecycle and simultaneous-press tests.
* Scoring boundary-condition tests.
* Recording integrity and project recovery tests.
* Rendering degradation and resource-cleanup tests.
* Dance-chart validation tests.
* Multiplayer synchronization and security tests.
* Browser and standalone-file compatibility matrix.
* Storage quota and project migration tests.
* Dependency failure and offline tests.
* Fault-injection strategy.
* Requirements-to-test traceability matrix.
* Final failure-recovery acceptance review.
Each entry must identify its dependencies, implementation deliverables, and objective pass/fail criteria.
13. Release-blocking acceptance gate
The implementation must not be declared production-ready if any of the following remains unresolved:
* Audio timing drifts during normal gameplay.
* Stuck notes can persist after stopping or changing modes.
* Valid supported MIDI files lose musical events.
* Saving can silently destroy an existing project.
* The advertised standalone file cannot perform its documented core functions.
* A rendering failure permanently disables audio or transport.
* Mobile controls fail to release inputs reliably.
* Multiplayer accepts invalid authoritative results without the intended validation.
* Required supported file formats have not been tested against a representative corpus.
* Critical errors are silently ignored or reported as successful operations.
Lower-priority features may be deferred only when their status is documented and the core acceptance criteria remain satisfied.
Versioning rule: Increment the specification patch version for clarifications and additional edge cases, the minor version for backward-compatible requirements additions, and the major version for changes to the product scope, architecture constraints, or acceptance contract. Record the date and summarize changes at the top of the document.


Specification version: FLM-1.2.0 | Last updated: 2026-10-23 | Status: Product improvement proposal | Scope: Essential improvements to gameplay, architecture, audio fidelity, usability, and release quality
Finger Lickin Music — Essential Product Improvements
The objective is to make Finger Lickin Music feel like a cohesive, professional music game rather than a collection of separate features. The following improvements address the capabilities that most strongly affect playability, musical accuracy, creative freedom, and long-term usability.
A distinction is important: no optional feature is literally necessary for every player. Here, “necessary” means an improvement is required to deliver the intended quality, reliability, or coherence of the product as specified.
1. Fix the core product architecture before expanding features
1.1. Create one unified musical engine
All modes must use the same underlying musical timeline, event model, audio scheduler, instrument definitions, and transport controls. Rhythm mode, free play, studio, imported songs, and dance mode should be different experiences built on shared foundations.
Why it matters: Prevents timing inconsistencies, duplicated logic, and bugs that appear only when switching modes.
1.2. Separate musical data from gameplay mappings
Preserve the complete original arrangement independently of the four-button chart, difficulty settings, or selected instrument.
Why it matters: Players can simplify a difficult song for gameplay without destroying the underlying composition.
1.3. Separate audio, rendering, and animation clocks
Musical events must be scheduled against the audio clock. Visuals must follow the musical timeline without controlling it.
Why it matters: Prevents missed notes, inaccurate scoring, and synchronization drift when the 3D scene becomes expensive to render.
2. Make the four-button gameplay genuinely musical
The four-button concept should be a central design strength, not a limitation that makes every instrument feel identical.
2.1. Introduce a universal musical control system
Support multiple mapping profiles:
* Four independent note lanes.
* Chord and interval buttons.
* Scale-based note selection.
* Instrument-specific mappings.
* Percussion triggers.
* Configurable custom layouts.
Allow players to switch profiles without modifying the original music.
2.2. Add adaptive difficulty that preserves musical intent
Difficulty should change the performance challenge rather than simply deleting random notes.
* Beginner: simplified rhythms, reduced chord complexity, and forgiving timing.
* Intermediate: more syncopation, chord changes, and rhythmic subdivisions.
* Advanced: denser patterns, sustain management, and more demanding timing.
* Expert: close correspondence to the source performance where the control scheme allows it.
When simplification is unavoidable, retain important beats, melodic contours, chord changes, and instrument accents.
2.3. Make every input feel responsive
Required improvements:
* Configurable input offset.
* Visual lead-time adjustment.
* Clear pressed and released states.
* Simultaneous button handling.
* Hold and sustain support.
* Immediate feedback for successful and missed inputs.
* Separate input latency and audio output compensation.
* Calibration tools that do not require the player to understand technical audio settings.
2.4. Add meaningful performance feedback
Show accuracy, combo, streaks, missed events, and section-by-section performance. Feedback should explain where the player can improve without overwhelming the play area.
The scoring system must be deterministic and independently testable.
3. Upgrade the sound system from functional to convincing
Audio quality will have an outsized effect on whether the game feels like a real musical instrument or a toy.
3.1. Implement a layered instrument engine
Use a suitable combination of sampled instruments, synthesis, and instrument-specific playback behavior. Support polyphony, velocity, sustain, program changes, percussion, pitch bend, and controller events where available.
Prioritize a reliable baseline across General MIDI programs over a few impressive instruments and dozens of unusable ones.
3.2. Add instrument-specific behavior
A guitar should not sound and respond like a piano with a different preset. Account for note decay, articulation, velocity response, playing range, sustain, and instrument-specific limitations.
Support legato or other advanced articulations where the selected sound engine can reproduce them.
3.3. Make mixing and playback reliable
Include track gain, master volume, mute, solo, pan, sensible peak management, and controlled voice allocation. Prevent clipping and runaway audio-node creation.
Audio must remain stable during dense arrangements and long recording sessions.
3.4. Add a sound-quality system with explicit fidelity levels
Every instrument should declare what it supports:
* Basic synthesized sound.
* Sample-based sound.
* Velocity layers.
* Articulation support.
* Controller support.
* Percussion-specific playback.
The UI should not imply that full General MIDI timbral fidelity is available when the application uses simplified synthesis.
3.5. Add audio diagnostics
Provide an optional calibration and diagnostics screen that measures or guides the user through:
* Audio output latency.
* Input response.
* Playback stability.
* Audio initialization.
* Sample or sound-bank availability.
Do not claim that browser software can accurately measure every component of a user’s hardware latency automatically. Where measurement is uncertain, provide a calibration procedure.
4. Make the 3D band a signature feature
The virtual band should be more than animated characters standing on a stage. It should be a visual interpretation of the actual music.
4.1. Build a reusable skeletal animation system
Use a consistent humanoid rig with instrument attachment points, reusable animation controllers, and procedural motion where appropriate.
Characters should have believable body movement and instrument interaction without requiring a separate bespoke animation system for every model.
4.2. Map musical events to instrument-specific actions
Map notes, velocity, rhythmic density, and sustain to meaningful actions: strumming, key presses, drum strikes, bowing, or other appropriate gestures.
If accurate hand-to-note animation is impractical, use a hybrid system combining skeletal animation with clear musical visualizations.
4.3. Add a performance director
A stage director should select camera angles, emphasize solos, react to song sections, and highlight important musical events.
Camera changes must not obscure essential gameplay targets or interrupt the player’s control.
4.4. Improve the visualizer with musical context
Add:
* Beat and measure indicators.
* Active-note highlighting.
* Instrument identity indicators.
* Velocity-responsive animation.
* Solo and accompaniment emphasis.
* Section transitions.
* Optional abstract effects for instruments without practical humanoid animations.
* Adjustable camera distance and stage layout.
Critical rule: The visualizer must never invent musical activity during silence or misrepresent inactive instruments as performing.
5. Turn the studio into a usable creative tool
The studio should allow a player to progress from a short musical idea to a complete multitrack composition without leaving the game.
Essential improvements
* Instant track creation: Add an instrument track and start recording with minimal navigation.
* Count-in and metronome: Support configurable count-in, tempo, and time signature.
* Overdubbing: Record a new instrument while hearing existing tracks.
* Loop recording: Repeat a section for practice and composition.
* Basic piano roll: Edit note pitch, start time, duration, and velocity.
* Quantization: Snap selected events to configurable rhythmic subdivisions without forcing all performances onto a grid.
* Undo and redo: Maintain a predictable edit history.
* Track management: Rename, duplicate, mute, solo, reorder, and delete tracks.
* Section markers: Label introductions, verses, choruses, bridges, and other sections.
* Project export: Save editable musical events separately from rendered audio.
5.1. Introduce a non-destructive editing model
Keep original imported data intact. Store edits as project changes or derived data, rather than destructively rewriting the source arrangement.
This makes it possible to reset mappings, compare edits, recover from mistakes, and switch gameplay modes without losing musical information.
5.2. Add a song arrangement overview
Display the full composition as a timeline containing tracks, sections, loops, and important events. Users should be able to navigate a long song without repeatedly scrubbing blindly.
5.3. Add a project recovery system
Use versioned project data, safe save operations, and recovery checkpoints. Warn users before destructive operations and offer an explicit recovery path when a save fails.
Local browser storage must not be presented as a guaranteed permanent backup.
6. Make imported music work reliably
File import is one of the product’s strongest differentiators, but also one of its largest sources of potential defects.
6.1. Add an import inspection screen
Before starting gameplay, show:
* Detected file format and version, where identifiable.
* Tracks and instrument assignments.
* Song duration and tempo information.
* Detected time and key signatures where available.
* Track event counts.
* Unsupported features and conversion warnings.
* Which track will be playable.
* Whether the arrangement requires a simplified four-button mapping.
6.2. Add an automatic playable-chart generator
The chart generator should derive playable patterns from the source arrangement using configurable rules.
For example, it can prioritize:
* Melodic contours.
* Chord roots and important chord tones.
* Strong beats.
* Rhythmic accents.
* Instrument-specific note patterns.
Users must be able to preview the generated chart and change the mapping before playing.
Necessary safeguard: Automatic chart generation must be deterministic for identical inputs and settings, and must not overwrite the original arrangement.
6.3. Add track isolation and practice tools
Allow players to:
* Mute the target instrument.
* Lower accompaniment volume.
* Solo an individual track.
* Loop a difficult section.
* Slow playback while preserving pitch where supported.
* Increase speed progressively.
* Restart from a measure or section.
* Practice one hand or one part where the instrument mapping supports it.
6.4. Publish an honest compatibility matrix
Explicitly list supported MIDI, MusicXML, Guitar Pro, and audio formats, including known limitations.
A format should not be advertised as supported merely because its file extension is recognized.
7. Make dance mode feel like a complete game mode
Dance mode should have its own presentation and progression rather than simply reusing instrument gameplay with different labels.
Essential improvements:
* Four-direction and configurable step layouts.
* Simultaneous steps and hold notes.
* Multiple difficulty levels.
* Timing judgments and combos.
* Song-specific charts.
* A distinct gameplay HUD.
* Avatar choreography synchronized to the chart.
* A practice mode with speed control.
* Chart validation and custom chart import.
* Accessible control alternatives.
Dance chart data, scoring, and choreography should remain separate systems connected through the common musical timeline.
8. Improve character customization and identity
Character customization is important to the band’s personality and multiplayer appeal.
Include:
* Preset characters.
* Body and silhouette choices.
* Color and material customization.
* Hair and clothing options.
* Accessories.
* Instrument selection.
* Stage positions.
* Saved character presets.
* Preview animations.
* Avatar compatibility checks.
The character editor should reuse the same rendering and rig systems as the gameplay stage.
Performance requirement: Customization must not cause a full scene reload or lose the current song, recording, or project state.
9. Add a proper progression and reward system
The game needs reasons to return after the novelty of the initial experience wears off.
9.1. Song and skill progression
Introduce:
* Song completion records.
* Best accuracy and score.
* Difficulty completion.
* Personal bests.
* Instrument-specific achievements.
* Dance achievements.
* Practice milestones.
* Optional challenge objectives.
Progression must reward improvement without locking core music creation tools behind grinding.
9.2. Performance history
Save results locally, including the song, difficulty, instrument, score, accuracy, and relevant settings. Allow users to compare attempts and identify improvement over time.
9.3. Unlockable cosmetics
Offer optional stage themes, avatar cosmetics, animations, and visual effects through progression.
Cosmetic unlocks should not affect gameplay accuracy, input timing, or instrument performance.
9.4. Daily challenges
Optional challenges can provide short, repeatable activities such as mastering a rhythm, playing a difficult section, or completing a song with a particular instrument.
Daily features must remain optional and must not require an account in standalone mode.
10. Make multiplayer robust and meaningful
Multiplayer should support more than seeing another player’s avatar.
10.1. Define three clear multiplayer experiences
Cooperative band
Players perform different instruments within the same arrangement. Show each player’s contribution and synchronize the musical timeline.
Competitive rhythm play
Players perform the same chart and compare accuracy, combos, and scores using identical chart versions and scoring rules.
Collaborative studio
Players contribute tracks to a shared project, with explicit ownership, edit permissions, and conflict handling.
10.2. Add synchronization diagnostics
The game should measure network latency and clock offset, detect missed updates, and communicate synchronization quality to players.
Musical events must be scheduled against a shared timeline, with suitable lead time, rather than played immediately when a network message arrives.
10.3. Add robust session recovery
Support reconnecting, resynchronizing song position, recovering room state, and handling host departure.
A disconnected player must not corrupt the session or permanently block other players.
10.4. Protect shared projects
Collaborative editing requires explicit rules for simultaneous edits, versioning, permissions, and conflict resolution. These rules must be defined before implementing shared studio functionality.
10.5. Keep multiplayer optional
Do not make account creation, server access, or a network connection necessary for local play, recording, or local project management.
11. Improve the interface and onboarding
A complex game can still feel simple if the initial experience exposes only the decisions that matter.
11.1. Introduce three levels of complexity
* Quick Start: Choose a song, instrument, and difficulty, then play.
* Customize: Change mappings, audio, controls, and visualization.
* Advanced: Access editing, detailed musical settings, chart generation, and diagnostics.
Do not expose every advanced control on the initial screen.
11.2. Use contextual controls
Show instrument settings when an instrument is selected, dance settings in dance mode, and track-editing tools in the studio.
Avoid a single enormous settings screen containing every feature.
11.3. Add an interactive tutorial
Teach the user to:
* Trigger a note.
* Play two simultaneous notes.
* Follow a simple rhythm.
* Select a different instrument.
* Record a short performance.
* Import a song.
* Enter the studio or dance mode.
Each step must be skippable, repeatable, and usable with either keyboard or touch.
11.4. Add clear loading and error states
Every loading screen must report real progress where measurable. Every error must explain what failed and what the user can do next.
The game must never silently ignore a failed import, recording, save, or connection.
12. Make mobile support a first-class design requirement
Mobile compatibility must be tested throughout development, not added after the desktop game is finished.
Essential improvements:
* Large, configurable touch controls.
* Reliable simultaneous presses.
* Correct handling of touch cancellation and focus changes.
* Portrait and landscape layouts.
* Adaptive rendering resolution.
* Adjustable sound-bank loading.
* Reduced visual effects on constrained devices.
* Persistent settings and recoverable projects.
* Clear audio activation behavior.
* Protection against accidental navigation during active play.
* Testing on actual iOS and Android devices.
12.1. Establish device performance profiles
Define at least three rendering profiles:
* High: full stage, richer lighting, and detailed animation.
* Balanced: reduced geometry and visual effects.
* Low: simplified scene and reduced animation complexity.
The audio scheduler must remain independent of these profiles.
12.2. Prevent resource exhaustion
Set explicit limits for simultaneous voices, loaded samples, active tracks, animation complexity, and project size. When a limit is reached, show a clear warning or use a documented fallback.
13. Add a professional reliability and recovery layer
This is essential because a music application can lose hours of user-created work through a single failed operation.
Required improvements
* Autosave at safe points.
* Recoverable recording sessions.
* Versioned project files.
* Validation before loading projects.
* Explicit save confirmation only after success.
* Undo and redo.
* Safe handling of failed exports.
* Resource cleanup when changing modes.
* Panic/stop control for all active notes.
* Diagnostics for audio, rendering, storage, and network errors.
* Automated regression tests for previously fixed bugs.
13.1. Introduce fault-injection testing
Deliberately simulate failures:
* Drop network connections.
* Suspend audio.
* Force a rendering interruption.
* Load malformed files.
* Exhaust storage.
* Interrupt a save.
* Disconnect an input device.
* Switch modes while notes are active.
Verify that the application recovers without corrupting user data.
13.2. Add a bug reproduction report
For development builds, provide a way to export diagnostic information such as browser capabilities, application version, active mode, relevant settings, and recent non-sensitive error events.
Do not include song contents, private files, or personal information unless the user explicitly chooses to attach them.
14. Improve the single-file architecture without sacrificing quality
The single-HTML-file requirement is useful for portability, but it must not become an excuse for a fragile architecture.
14.1. Use logical modules inside the HTML
Organize the application into clearly separated modules, even when all source code is embedded in one document.
Keep the following independently testable:
* Musical timeline.
* Input and mapping.
* Audio engine.
* File parsers.
* Rhythm scoring.
* Studio and recording.
* Rendering and animation.
* Dance gameplay.
* Character customization.
* Persistence.
* Multiplayer client.
14.2. Establish a strict dependency budget
For each dependency, record its purpose, version, license, size, loading strategy, and fallback behavior.
Prefer native browser capabilities where appropriate, but use reliable libraries for complex tasks such as parsing intricate music formats or rendering skeletal 3D animation when that meaningfully improves correctness.
14.3. Define two delivery profiles
Profile A — Standalone edition
Required
One HTML file containing the core application. Local gameplay, supported music import, local recording, visualization, and project export must work without an online service.
Profile B — Online edition
Optional infrastructure
The same HTML client with access to an external multiplayer service. Additional downloadable sound banks or assets may be used if their absence does not break the documented standalone functionality.
The online edition must not be misrepresented as entirely self-contained. A public multiplayer service cannot be created solely by embedding client-side code in an HTML file.
15. Add accessibility and customization beyond appearance
The game should let users adapt the experience to their needs.
Essential improvements:
* Remappable keyboard and touch controls.
* Adjustable note speed.
* Adjustable judgment windows where appropriate.
* Reduced-motion mode.
* High-contrast note indicators.
* Non-color-only lane identification.
* Adjustable visual effects.
* Scalable interface.
* Clear focus indicators.
* Keyboard navigation for menus.
* Configurable control sizes.
* Optional simplified visualization for lower-powered devices.
Accessibility settings must be applied consistently across instrument, studio, and dance modes.
16. Make the game easier to extend
The product will become difficult to maintain if each new instrument, file format, avatar, or gameplay mode requires modifying several unrelated systems.
16.1. Use data-driven instrument definitions
Each instrument definition should describe, as applicable:
* Display name.
* General MIDI program.
* Sound-bank mapping.
* Percussion behavior.
* Playable range.
* Polyphony requirements.
* Input mapping defaults.
* Animation profile.
* Visual representation.
* Supported controllers and articulations.
Adding an instrument should primarily involve adding or updating its definition and required assets, not rewriting the audio scheduler.
16.2. Use adapters for music formats
Each importer should convert its source into the shared internal music representation. The rest of the game should not need to know whether a song came from MIDI, MusicXML, or Guitar Pro.
16.3. Use a consistent event system
Musical events should be consumable by audio playback, scoring, visualization, recording, and animation without duplicating or modifying the original source event.
16.4. Version all persistent data
Instrument definitions, project formats, mappings, dance charts, and multiplayer messages must have explicit versioning and migration rules where appropriate.
17. Add automated quality gates
Do not wait until the application appears complete to discover that its foundational systems are unreliable.
The implementation must automatically verify:
* Musical time conversion.
* Audio scheduling logic.
* Note-on and note-off lifecycle.
* Chord and scale mapping.
* Scoring boundary conditions.
* MIDI parsing.
* Project save/load integrity.
* Import/export round trips where supported.
* Mode-transition cleanup.
* Multiplayer message validation.
* Mobile input lifecycle.
* Resource limits.
Every defect fixed after testing should receive a regression test whenever practical.
The final release must also be tested by opening the actual delivered HTML file, not just running an intermediate development version.
