## 7. User interface and navigation

This part fixes everything the player sees and touches: the visual rules, the three
complexity levels, where each setting appears, the navigation model, the responsive
layouts, every screen (`SCR-*`) and dialog (`DLG-*`) with element ids, layouts, states and
exact texts, the HUD, onboarding and the tutorial, the accessibility implementation, and
the text catalog. Module APIs named here belong to Part 4 and Part 6; screen controller
logic is M-27 (Part 6.27), widgets and the screen stack are M-26 (Part 6.26). Design tokens
are Part 3.2.2 and are referenced, never redefined.

Conventions used in this part:

- Element ids. A screen root is `#scr-<slug>` where `<slug>` is the screen name after
  `SCR-` in lower case (`#scr-mainmenu`); a dialog root is `#dlg-<slug>`. Child elements use
  a fixed per-screen prefix: `fl` FirstLaunch, `mm` MainMenu, `qp` QuickPlay, `ins`
  Instrument, `fp` FreePlay, `st` Studio, `lib` Library, `imp` ImportInspect, `dn` Dance,
  `mp` Multiplayer, `ch` Characters, `set` Settings, `hlp` Help, `ab` About, `dg`
  Diagnostics, `tut` Tutorial, `res` Results, `ps` Pause, `hud` HUD, `pad` touch pads.
  Ids are unique in the document at any time (a screen's DOM exists only while mounted).
- Texts in double quotes are exact user-facing strings. A text with a code (`E-...` error,
  `S-...` status) is reproduced in the catalog of 7.11, which governs when the two differ.
  Placeholders are `{name}`. Labels of buttons and fields are given in the element tables
  and are exact as well.
- "Back" means the screen's back action. It is triggered by the on-screen Back button
  (`g-back` icon, label "Back"), `Escape` (outside gameplay), gamepad button 1 in menus,
  and the browser back button (7.4). Each screen states what Back does.
- Keyboard maps list keys by `KeyboardEvent.code`. Gameplay keys are the M-07 maps (Part 6.7,
  remappable); every other key in this part is a fixed UI key handled by M-26 or M-27.
- Sizes are CSS px at `--ui = 1` unless given as tokens; tokens scale with `--ui` (3.2.2).

### 7.1 Visual identity

#### 7.1.1 Direction

Finger Lickin Music looks like a small club stage seen from the mixing desk: a near-black
room (`--c-bg`), graphite panels (`--c-panel`, `--c-panel-2`) and one warm spotlight amber
(`--c-accent`) that marks the single thing to do next. Color is information, not
decoration: amber means "primary action or selected", cyan (`--c-accent-2`) means
"informational", green, yellow and red mean status, and the four lane colors appear only
where a lane or dance direction is meant, always together with its glyph (circle, triangle,
square, diamond; arrows for dance). The 3D stage carries the energy (lights pulse on
`sched.beat`, performers move on `sched.noteOn`); the interface around it stays flat,
quiet and legible so the music and the note highway dominate (P 2.1). The logo is the game
name set in `--fs-6` `--fw-bold` with the four lane glyphs in a row beneath it at `--fs-4`;
it appears on SCR-FirstLaunch, SCR-MainMenu and SCR-About only.

#### 7.1.6 Hierarchy rules

1. Each screen has exactly one `.btn.primary` (or one primary card) visible at a time; it is
   the next step of the current task ("Play", "Start", "Record", "Import", "Save").
2. Secondary actions are `.btn`; destructive actions are `.btn.danger` and always lead to a
   confirmation dialog that states the consequence (7.7).
3. The screen title (`h1`) names the current task; the current song or project name is
   shown under it in `--fs-2` (B 6.3 "current mode" and "current song or project").
4. Status (save state, connection, storage notices, audio state) is shown with an icon,
   a status word and a semantic color, in a fixed place per screen (top bar right).
5. Advanced controls live behind a disclosure ("More options", "Advanced") or in the
   Settings category "Advanced" and are never on the first visible screenful of
   SCR-QuickPlay (I 11.1).
6. Informational labels are never styled like buttons: no border, no hover change, no
   pointer cursor.

#### 7.1.7 Forbidden

- Gradients of any kind on UI surfaces, text or the HUD (`linear-gradient`,
  `radial-gradient` are not used in `S02` to `S05`; the blob-shadow texture of the 3D stage
  is a renderer texture, not UI).
- Glow: no colored `box-shadow` with blur, no `text-shadow` other than the HUD readability
  shadow `0 1px 2px rgba(0, 0, 0, 0.8)` on `#hud` text, no `filter: drop-shadow` or `blur`,
  no `backdrop-filter`.
- Decorative borders, double borders, ornaments, background images and patterns.
- More than one accent-colored element competing on one screen (rule 7.1.6.1).
- Color as the only carrier of meaning (7.10); emoji or non-ASCII symbols in UI text.
- Animations that run continuously without a musical event or a loading state (7.1.5).
- Fake progress: percentages that are not measured (B 20.4, P 21).

### 7.2 Complexity levels (I 11.1)

The three levels are structural, not a global switch: each level is a set of places, and a
player moves to the next level by opening it. Nothing is hidden permanently; nothing
advanced is on the first screenful of the Quick Start path.

| Level | Where it lives | What it exposes | What it never shows |
|---|---|---|---|
| Quick Start | SCR-MainMenu entry "Quick Play"; SCR-QuickPlay in `level:'quick'`; SCR-Dance select state; SCR-FirstLaunch "Play a demo song" | Song list, part list (instrument tracks and "Dance"), difficulty, the Play button; master volume in the top bar | Profiles, chart preview, judgment presets, practice tools, calibration values, any number field |
| Customize | SCR-QuickPlay "More options" disclosure (open by default when entered from "Instrument Mode", `level:'customize'`); SCR-Pause practice panel; SCR-Settings categories Audio, Controls, Gameplay, Video, Accessibility, Calibration; SCR-Characters; SCR-FreePlay settings panel | Mapping profile, control layout, backing tracks, target track level, visualization on or off, speed and loop practice, count-in, chart preview per difficulty, audio and input settings, camera, appearance | Track editing, chart generation parameters, raw diagnostics |
| Advanced | SCR-Studio; SCR-ImportInspect "Tracks" and "Chart" tabs; SCR-Settings category "Advanced"; SCR-Diagnostics (reached from Settings > Advanced or `?diag`) | Multitrack editing, piano roll, quantize, mixer, markers, per-track chart generation with profile and difficulty preview, polyphony cap, chord window, stats overlay, log level, diagnostics export, self-test (test build) | n/a |

Rules: (1) the Quick Start path from the main menu to sound is at most two activations after
the audio unlock (Quick Play, Play: the default selection of Part 1.7 is preselected);
(2) the "More options" disclosure remembers its open state per session only (not persisted);
(3) every Customize control that changes scoring comparability carries the badge "Not
comparable" next to its value when set off-default (7.10.1).

### 7.4 Navigation model

#### 7.4.1 Screens, modes and the stack

The screen stack (`FLM.UI.Screens`, M-26) holds mounted screens in `#overlay`; the root is
always SCR-MainMenu (depth 1). Each mode of Part 4.7 pushes its root screen above the menu
on enter; SCR-Pause and SCR-ImportInspect sub-states are screens pushed above their mode
screen; dialogs are not stack entries (they live in a dialog layer inside `#overlay` and
are counted by `UI.dialogCount()`). Only the top screen receives input; covered screens keep
their DOM (hidden with `hidden`) so their filters, selection and scroll are preserved.

| Operation | Effect on the stack | Effect on history | Used by |
|---|---|---|---|
| `push(id, params)` | mounts and shows `id` above the top; the previous top gets `hidden` and records its focused element | `history.pushState({flm:1, seq:depth-1, screen:id}, '')` | mode enter, opening a sub-screen (SCR-Pause, SCR-ImportInspect from Library) |
| `replace(id, params)` | unmounts the top, mounts `id` at the same depth | `history.replaceState` with the same `seq` | a mode swapping its own root screen: SCR-Multiplayer lobby -> the multiplayer play layout at the countdown and back to the lobby after the song (Part 4.7.2 step 12) |
| `pop()` | runs the top screen's back guard (7.4.3); on pass unmounts it, shows the one below and restores its focus | internal pops call `history.back()` once with the suppress counter incremented (7.4.2) | Back button, `Escape`, gamepad B |
| `popTo(id)` | pops without guards down to `id` (guards already ran in the leave sequence) | `history.go(-(n))` for the n entries removed, suppressed | `Modes.leave` (Part 4.7.2 step 10) |
| `back()` | `pop()` unless the top screen overrides back (gameplay screens open SCR-Pause instead, SCR-Pause resumes) | as `pop` or a `pushState` for SCR-Pause | the global back entry point, also the `popstate` handler |

Mode changes always go through `FLM.Modes.enter` and `leave` (Part 4.7); a screen never
pushes another mode's root screen directly. Leaving a mode ends at SCR-MainMenu and the
next mode's root is pushed fresh, so the stack never holds two mode screens.

#### 7.4.2 Browser back and forward

1. At boot (M-28 `init`, Part 4.3 B10) the current history entry is replaced with
   `{flm:1, seq:-1, sentinel:true}` and one entry `{flm:1, seq:0, screen:'SCR-MainMenu'}`
   is pushed, so the first browser back at the menu stays inside the page.
2. Every `push` adds one entry with `seq = depth - 1`; `replace` replaces the top entry.
3. `popstate` handler: if the suppress counter is > 0, decrement it and return. Otherwise
   `target = event.state && event.state.flm ? event.state.seq : -1` and `top = depth - 1`:
   - `target < top`: call `UI.Screens.back()` once. If the back is refused (guard
     cancelled, or the top screen handled it as pause or resume), re-push the entry for the
     current top so the browser history matches the stack again. A jump of several entries
     at once (long-press history menu) is processed as one `back()`; the remaining entries
     are re-synchronized by pushing the stack's entries above the new top.
   - `target > top` (browser forward into an entry whose screen was already unmounted):
     forward is not replayable; call `history.go(top - target)` with the suppress counter
     incremented, which returns the browser to the current entry. Nothing else happens.
   - `target === top`: nothing.
   - `target === -1` (sentinel reached at SCR-MainMenu): push `{seq:0}` again and show toast
     S-GEN-01 "Press back again to leave Finger Lickin Music."; a second sentinel hit within
     2 s does not re-push, so the browser leaves the page (with the unload guard of 7.4.3
     when a project is dirty).
4. Gameplay screens (SCR-Instrument, SCR-Dance, SCR-Tutorial play steps, multiplayer play):
   browser back pauses (pushes SCR-Pause) instead of leaving; on SCR-Pause browser back
   resumes (same as `Escape`). Quitting gameplay is an explicit "Quit" button.
5. Fallback (Part 1.6): when `history.pushState` throws (some `file://` contexts), M-28
   switches to hash navigation for the session: each push sets `location.hash =
   '#/' + seq + '/' + screen` and a `hashchange` listener applies rule 3 with `seq` parsed
   from the hash. The internal stack works identically either way.

#### 7.4.3 Unsaved-changes guard points

`FLM.UI.confirmUnsaved(info)` shows DLG-UnsavedChanges with `FLM.Project.guard.describe()`
text and resolves to `'save'`, `'discard'` or `'cancel'`. The guard runs at these points and
nowhere else:

| Guard point | Condition | Choices and outcome |
|---|---|---|
| Back from SCR-Studio (any trigger) | `Project.isDirty()` | Save (saves, then leaves when `project.saved` arrives; on `project.saveFailed` the leave is cancelled and DLG-SaveFailed shows), Discard (leaves; the checkpoint ring keeps the last autosave), Cancel (stays) |
| Back from SCR-FreePlay | the transient Free Play project holds a take not yet saved or opened in Studio | Save opens the project name field then saves; Discard drops the transient project; Cancel stays |
| SCR-Library "Open" of another project, "New project" in Studio | current project dirty | as Studio |
| SCR-ImportInspect "Play now" or "Open in Studio" | a project is open and dirty (both actions make the imported song the current project) | DLG-ImportReplace (7.7), not DLG-UnsavedChanges; "Save to Library" only adds a catalog entry and never asks |
| SCR-Settings "Data and backup" > "Import settings" | always | DLG-ImportSettings (7.7) |
| Page unload (`beforeunload`) | `Project.isDirty()` and not recording | the listener sets `event.returnValue = ''` (browser's own prompt; custom text is not shown by browsers); `pagehide` also triggers the synchronous autosave of Part 4.7.4 |
| Mode leave caused by an error (`returnToMenu`) | any | no dialog: the leave autosaves (Part 4.7.2 step 13) and the project stays in memory |

Characters (SCR-Characters) never asks: changes are applied as they are made (Part 1.2).
Recording in progress is never interrupted by a guard dialog: Back while recording first
stops the take (S-STU-04 "Recording stopped. The take was kept.") and then applies the
guard.

#### 7.4.4 Focus restoration

1. On `push`, the covered screen stores the id of its focused element (or its scroll
   container plus row index for lists). On `pop`, that element regains focus; if it no
   longer exists, the screen's initial focus target is used.
2. Each screen names its initial focus target in 7.6 ("Initial focus"); a screen that names
   none focuses its first focusable control after the Back button. The target is focused
   when the push transition starts (same frame), with `preventScroll: true`.
3. Dialogs: `UI.Focus.trap(dialog)` on open (Tab and Shift+Tab cycle inside; focus starts
   on the dialog's default button, which is never a destructive one); on close focus returns
   to the invoking element via `UI.Focus.restore()`, or to the screen's initial focus
   target when the invoker was removed.
4. Gameplay: when play starts, `document.activeElement.blur()` runs (no text field keeps
   focus, B 6.4) and focus moves to the gameplay surface `#view` (`tabindex="-1"`), so
   `Escape` and the lane keys reach M-07.
5. The focus ring is the Part 3.2.4 `:focus-visible` ring; `.focus-ring` is added by M-26
   to the focused element after keyboard or gamepad navigation so the ring is also visible
   on browsers where programmatic focus does not trigger `:focus-visible`.

#### 7.4.5 Listener discipline

Screens attach every DOM listener through `FLM.Core.dom.on(el, type, fn, opts, owner)` with
the screen's owner token, and every bus subscription with the same token; `unmount` calls
`Core.dom.offOwner(owner)` and `bus.removeOwner(owner)` and removes the screen's DOM. M-26
installs exactly one document-level `keydown` listener (UI navigation) and one
`pointerdown` capture listener (audio unlock, Part 4.3 B15) at `UI.init`; screens register
key handlers with M-26 instead of adding their own document listeners. Repeated navigation
therefore cannot accumulate listeners; `Modes.assertClean()` (Part 4.7.3) checks the
counts after every leave (P 3 "repeated navigation does not duplicate event listeners").

Screen-level single-key shortcuts (for example `Space` play and stop in SCR-Studio) are
ignored when the key code is bound to a live control in the current `FLM.Input` context
(checked by M-27 through `FLM.Input.getMap()` and `FLM.Input.context()`), so a remapped
gameplay key never triggers a UI action as well.

Gamepad in menus: while a gamepad is connected (`input.device`) and the mode is not a
gameplay mode, M-27 polls `navigator.getGamepads()` every 50 ms with a `Core.timers`
interval owned by `'ui-gamepad'` and translates edges to UI navigation: d-pad (buttons
12-15) moves focus like the arrow keys, button 0 activates, button 1 is Back, button 9
(start) activates the screen's primary button. The interval stops on disconnect and when a
gameplay mode is entered (M-07 owns the pad there).

### 7.5 Responsive rules

#### 7.5.1 Layout families

The layout family is computed by M-26 from the viewport and published in `ui.layout`. The
classes are those of Part 3.2.3 plus one media query.

| Family | Condition | Class and query | Layout pattern |
|---|---|---|---|
| Phone portrait | `min(innerWidth, innerHeight) < 600` and portrait | `body.compact.portrait` | one column; full-screen gameplay; settings and editors in sheets or tabs; pads along the bottom |
| Phone landscape | `min(...) < 600` and landscape | `body.compact.landscape` | two columns where useful (list plus detail); gameplay with pads at the bottom or right |
| Tablet | `min(...) >= 600` and `innerWidth < 1024` | neither `compact` nor the wide query | two columns; panels as side drawers |
| Desktop | `innerWidth >= 1024` and `min(...) >= 600` | `@media (min-width: 1024px)` with `body:not(.compact)` | multi-panel: navigation column, stage or editor center, inspector right (B 6.4) |

Viewports the layouts are checked at (Part 2.13 LT list): 360 x 640, 390 x 844, 844 x 390,
768 x 1024, 1024 x 768, 1366 x 768, 1920 x 1080. At every one of them and at `--ui` 0.8 to
1.5: no horizontal page scroll (`html, body { overflow: hidden }` plus scroll containers that
scroll vertically only), no clipped text, no overlapping controls (P 2.2). Scroll containers
set `overflow-y: auto; touch-action: pan-y; overscroll-behavior: contain` because `body` has
`touch-action: none` (Part 3.2.4).

#### 7.5.2 Touch targets

- On `body.touch` every interactive control is at least `var(--touch-min)` (56 px) on both
  sides with at least `--sp-2` (8 px) between hit areas (brief section 6). The visible shape
  may be smaller (a 24 px toggle thumb) when the hit area is padded to 56 px.
- On pointer-only layouts menu controls are at least 44 x 44 px (Part 2.13 decision 6).
- Gameplay pads: minimum height from `input.padSize` (small 56, medium 72, large 88 px),
  width as computed below, never below 56 px.
- Nothing essential depends on hover (B 21.1): every `.hover-only` element (tooltips) has a
  tap or focus equivalent.

#### 7.5.3 Pad placement

Pads are four `div.pad` children of `#touch` with ids `pad-0` to `pad-3` (lanes 0-3, or
dance directions 0-3 in SCR-Dance). `UI.TouchPads.layout(mode)` computes rectangles from
the viewport, the safe areas and the settings, then calls `FLM.Input` to refresh its cached
rects (`Input.layoutChanged()`, Part 6.7.4 D.2) through M-27.

| Orientation and `input.padLayout` | Area | Arrangement | Highway area |
|---|---|---|---|
| Portrait (any setting) | bottom 28 % of the viewport height, but at least the pad minimum height + 16 px, inside the safe areas | one row of four equal pads, 8 px gaps, 8 px side margins; lane 0 at the left | the full width above the pad area; hit line 12 px above the pads' top edge |
| Landscape, `bottom` | bottom 24 % of the height (same minimum) | one row of four pads split into two pairs: lanes 0-1 in the left 40 % of the width, lanes 2-3 in the right 40 %, 20 % center gap | centered column, 40 % of the width, above the pad row; hit line 12 px above the pads |
| Landscape, `right` | right 24 % of the width, full height minus the top bar | 2 x 2 grid: top row lanes 0 and 1, bottom row lanes 2 and 3, 8 px gaps | left 76 % of the width, highway centered there; hit line at 80 % of the height |
| Dance, any orientation | as the instrument row above, with `layout:'pads'` rendering a 2 x 2 diamond (up top, left and right middle, down bottom) inside the same area when `session.dance.layout === 'pads'` | arrows layout: one row left, down, up, right | as instrument |

Each pad shows its glyph (`g-lane0`..`g-lane3`, or the arrow) at 40 % of the pad height,
centered, plus a small label: the current note name or chord name in Free Play (from
`Mapping.profileTable`), nothing in chart play. Background `--lane-N` at the opacity of
`input.padOpacity`, border 2 px `--lane-N`; class `pressed` (set by M-26 on `input.event`
press, removed on release) raises opacity to 1 and inverts the glyph color to `--c-bg`. The
highway and HUD never place anything under the pads; the pads never cover the hit line.

Pads are shown when `Caps.maxTouchPoints > 0` (body class `touch`) or when
`onboarding.inputMode === 'touch'`, and hidden in the keyboard layout chosen at first launch
(`desktop`); SCR-Pause offers "Show touch pads" either way.

#### 7.5.4 Rotate recommendation

Modes that recommend landscape on phones: `instrument` and `quickplay` play (four lanes plus
stage), `multiplayer` play, `studio` (piano roll width). `dance`, `freeplay` and every panel
mode are designed for portrait and never recommend rotation. Rule: when one of the
recommending modes is entered and `body.compact.portrait` holds, `#rotate` is shown with its
Part 3.2.5 text ("Landscape recommended" / "This mode works best with the device sideways.
You can keep playing in portrait." / button "Continue in portrait"). It is shown before play
starts (gameplay waits with the count-in until the panel is dismissed or the device is
rotated), at most once per mode per session, and never during active play. Rotating to
landscape hides it automatically. Nothing is ever blocked: every mode is fully usable in
portrait (B 6.4).

#### 7.5.5 Safe areas, UI scale and text entry

- Safe areas: `#overlay`, `#hud` and `#rotate` pad with the `--safe-*` tokens (Part
  3.2.4); pads are placed inside `env(safe-area-inset-*)`; the top bar of every screen has
  `padding-top: var(--safe-top)` included in its 56 px height on notched devices.
- UI scale: `video.uiScale` sets `--ui` (0.8-1.5, step 0.05) through `UI.Layout.setScale`;
  all rem-based tokens follow. At 1.3 and above on `body.compact`, multi-column grids
  (menu landscape grid, Library two-pane, Characters options grid) collapse to one column
  and the HUD hides the section name line (kept in the progress bar tooltip and the
  screen-reader live region).
- Text entry is limited to: project name, track name, marker label, character name, preset
  name, player display name, invite and answer codes (paste), relay URL (Online edition),
  library search. None is required to start any mode; every name has a default. Text
  fields use `maxlength` from the data limits (track 80, project 80, marker 80, character
  24, display name 24, search 60), `autocomplete="off"`, `autocapitalize="sentences"`
  (names) or `"off"` (codes), `spellcheck="false"`, `enterkeyhint="done"`. During gameplay
  no text field exists in the DOM (B 6.4); Studio text fields commit on Enter or blur and
  are blurred when recording starts.
- Long names: a single-line CSS ellipsis (`white-space: nowrap; overflow: hidden;
  text-overflow: ellipsis`) everywhere in lists, track headers and top bars, with the full
  text in `title` and in the accessible name. Text drawn into the canvas or the HUD uses
  `UI.truncate(text, maxChars)`, which cuts at `maxChars - 3` and appends "..." (ASCII):
  HUD song title 32, performer label 16, lobby name 24, results song title 48. Names never
  wrap into a second line inside fixed-height rows (P 21).

#### 7.7.1 DLG-Calibration wizard

Goal (I 2.3, I 3.5, B 8.5): measure the two offsets of Part 5.12 without technical terms,
and preview the third. Width `min(96vw, 40rem)`. The wizard uses the metronome click on
`Transport.main` (Part 1.2 settings row) and reads taps from `input.event` (Input context
`instrument`, any lane control counts as a tap; the pads are shown on touch devices). It
never claims an exact hardware measurement (I 3.5); the result is a calibration.

| Step | Title and instruction (exact) | Procedure | Result |
|---|---|---|---|
| 1 | "1. Listen and tap" - "Close your eyes if it helps. Tap any lane key or pad on every click you hear. The first four clicks are for getting into the rhythm." | 12 clicks at 90 BPM (667 ms apart), accent on every 4th; the screen shows only a counter "Click {k} of 12" (no flashing, so only hearing is measured); taps are matched to the nearest click within +/- 300 ms; taps on clicks 1-4 are ignored | `A` = median of `(tap.tAudio - click.audioTime) * 1000` over the matched taps of clicks 5-12 (at least 6 needed) |
| 2 | "2. Watch and tap" - "Now there is no sound. Tap when the circle flashes on the line." | 12 flashes of the hit-line circle at 90 BPM drawn at the scheduled audio time (no audio); same matching and ignoring rules | `V` = median of `(tap.tAudio - flash.audioTime) * 1000` |
| 3 | "3. Note speed" - "Notes should reach the line exactly when you hear them. Choose a speed that is comfortable to read." | a 4-lane highway preview loops 8 notes with clicks, using the new values; slider "Note speed" (7.3) | `visualLeadMs` |
| Summary | "Your calibration" - "Sound delay: {audioLatencyMs} ms. Tap timing: {inputOffsetMs, with sign} ms. Note speed: x{s}." plus "Browser estimate of the sound delay: {estimate} ms." from `Audio.latency()` and two number fields to adjust both values manually | `audioLatencyMs = clamp(round(A - V), 0, 500)`, `inputOffsetMs = clamp(round(V), -200, 200)`; the judge offset therefore equals `A` (Part 5.12) and the highway delays notes by `audioLatencyMs` | "Save"* (writes the three keys with `source:'wizard'`), "Back", "Cancel" E |

Quality checks per step: fewer than 6 matched taps -> S-CAL-01 "Not enough taps were
counted. Tap on each click, then try again." with "Try again"; interquartile range of the
deltas above 40 ms -> S-CAL-02 "Your taps were uneven, so the result may be off. Try again
for a steadier result." with "Try again" and "Use anyway". Step buttons: "Start" (primary,
starts the clicks after a 1 s pause), "Skip this step" (keeps the current value), "Back",
"Cancel" E. During steps 1 and 2 `Escape` cancels the run of that step only. Opening the
wizard while a song is paused (SCR-Pause) is allowed; saving marks that run not comparable
(Part 6.9.5).

#### 7.8.2 Judgment feedback and non-color cues

Every judgment is shown in three redundant ways: the word, a shape at the lane's hit point,
and the color (B 22 "non-color-only indications of success and failure").

| Judgment | Word (`hud-judgment`, `--j-*` color) | Shape at the hit line of each lane of the note | Timing word |
|---|---|---|---|
| perfect | "Perfect" | a full ring around the lane glyph, 100 % size, 150 ms | none |
| great | "Great" | a ring at 75 % size | "Early" or "Late" when `abs(deltaMs) > perfect window` |
| good | "Good" | a ring at 50 % size | "Early" or "Late" |
| miss (head) | "Miss" | an X (`g-close` shape) over the lane glyph; the missed note turns to `--c-text-dim` and continues off the line | none |
| miss (hold tail) | "Hold break" | the hold tail turns to `--c-text-dim` from the break point | none |
| stray press (no note) | no word | the pad and lane glyph flash with a dashed outline (no ring) | none |

Rules: the newest judgment replaces the previous word immediately (no queue); a chord shows
one word (the chord's judgment, Part 6.9.4 B.8); while a hold is held its tail is drawn at
full lane color and the word "Hold" shows under the combo; `gameplay.showJudgmentText` off
hides words but keeps shapes; `accessibility.largeJudgmentText` scales the word to 125 %;
the screen-reader region does not read individual judgments (7.8.6).

#### 7.8.3 Combo display rules

- The combo appears at 4 consecutive hits ("4 combo") and updates in place on each hit.
- Every 50th combo shows the milestone word "{n} combo!" for 1 s (scale pulse 1.0 -> 1.1
  over `--t-fast` without reduced motion).
- A miss after a combo of 10 or more shows "Combo lost at {n}" in `--fs-2` for 800 ms under
  the judgment; below 10 the combo simply disappears.
- The score multiplier is shown as "x2", "x3", "x4" next to the score (Part 6.9.4 E.4) and
  returns to nothing at x1.
- Combo text never covers the four lanes' lower 20 % (the area where notes are judged).

#### 7.8.4 Section and failure feedback

- At each section boundary (`sched.marker`) the finished section's accuracy is shown at the
  side of the highway for 2 s as "{label}: {accuracy rounded to an integer} %"; it never
  overlaps the lanes.
- Failure feedback is informative, not punitive (P 5.2): the word "Miss" without sound
  effects or screen shake; after 8 misses in a row the hint S-PLAY-07 "Too fast? Pause to
  slow down, loop this section, or try an easier difficulty." appears once per play-through
  for 3 s at the side.
- Dance with life bar: the bar drains per miss (Part 6.23 failure rule); at 20 % it shows
  the word "Low"; at 0 the song ends with S-DNC-01.
- Song end: "Song complete" (S-PLAY-01) for 1.5 s, then SCR-Results.

#### 7.8.5 Pause and restart

- Pausing (any trigger) freezes the highway at the paused tick, hides `hud-judgment` and
  `hud-combo` milestones, and pushes SCR-Pause; the Judge is inactive (Part 6.9.4 B.1), and
  held controls were released with `source:'system'` (Part 4.7.4), so no press during the
  pause is judged or counted as a stray (P 5.2).
- Resume uses the three-beat countdown of 7.6.18.
- Restart and Retry run the full leave and enter sequence; `HUD.reset()` sets the score to
  0, hides the combo and judgment, empties the progress bar, clears the section label and
  the peers' values, and the new Judge starts from a fresh `load` (Part 6.9.3 invariant 5),
  so no stale scoring state is reused.

#### 7.8.6 Screen-reader announcements

When `accessibility.screenReaderLabels` is on, `hud-sr` announces, politely and at most one
message per 2 s: the count-in start ("Get ready"), section changes ("Chorus"), combo
milestones every 50, pause and resume, the song end, and in multiplayer joins, leaves and
the start countdown. Individual judgments are not announced (they would flood the reader);
the results screen announces the full summary.

#### 7.10.1 Comparability flag (P 5.3)

A run is comparable only when the judgment preset is Standard, the speed is 100 %, the
extra-press penalty is off, calibration was not changed during the run, and the song was
finished (Part 5.13 `comparable`, Part 6.9.4 G). The UI makes this visible in three places:
the badge "Not comparable" next to any off-default value in SCR-QuickPlay, SCR-Dance and
SCR-Pause; the SCR-Results line "Not counted for personal bests: {reasons}"; and the history
list (comparable runs only feed personal bests and the daily challenge). Multiplayer forces
Standard windows and 100 % speed for every player (Part 5.16 `ready` validation) and shows
S-NET-13 "Multiplayer uses standard timing windows and normal speed so scores are
comparable." in the lobby when a player's local setting differs. Accessibility adjustments
are never hidden or disallowed in single-player; they are labeled.

### 7.11 Text catalog

#### 7.11.1 Rules

1. Home in code: every string of this catalog lives in one frozen table `FLM.Core.Text`
   (data block at the end of `src/01-core.js`) with `get(code, params) -> string`,
   `has(code) -> boolean` and `all() -> object`. Reason: M-01 is the only module every other
   module may reference (Part 4.2 R-DEP), and `ErrorReporter.report` fills `userMessage`
   from the catalog at report time (Part 4.9). Module tables such as `FLM.Import.ERRORS`
   hold codes and classes and read their text from `Core.Text`, so a string exists once.
   `get` replaces `{name}` placeholders from `params`; a missing parameter becomes an empty
   string and is logged once; an unknown code returns E-GEN-000 text with the code.
2. Every error text says what failed and what the player can do next (I 11.4, P 15 "error
   messages identify the affected operation"); dialogs add the code in `.code` under the text;
   toasts for `E-*` codes show the code in `--fs-1` after the text; `S-*` texts never show a
   code.
3. No text exposes stack traces, file paths, internal ids, byte offsets beyond the
   `{detail}` the parsers already limit, or anything from the user's files other than the
   file name and titles (P 19 "avoid exposing sensitive information"). Imported text
   (titles, track names, warning details) is always inserted with `textContent` (ADR-12).
4. Number formats (fixed, independent of the browser locale so screenshots and tests are
   stable): integers with "," thousands separators ("12,450"); accuracy with two decimals
   ("97.42 %"); other percentages as integers ("75 %"); times by `Core.formatTime` ("3:12",
   "-0:02" during count-in); sizes "{n} KB" below 1 MB (integer) and "{n.n} MB" above;
   milliseconds as integers with "ms"; signed offsets with an explicit sign ("+12 ms",
   "-8 ms"); BPM with at most one decimal ("120 BPM", "73.5 BPM").
5. ASCII only; the ellipsis is "..." and the multiplication sign is "x".
6. Warning texts `W-*` are owned by the modules that produce them (Part 6.3, 6.10 to 6.14,
   Part 5.6) and are shown verbatim in SCR-ImportInspect and SCR-Diagnostics; they are not
   repeated here.

#### 7.11.4 Toast behavior

`FLM.UI.toast(text, {kind, action, durationMs})` with kinds `info` (3 s), `success`
(2.5 s), `warn` (5 s) and `error` (8 s); a toast with an action button stays 10 s. At most
3 toasts are visible (newest at the bottom; on gameplay screens the stack moves to the top
center below the progress bar so it never covers pads or the hit line: `body.in-game #toast
{ top: calc(var(--safe-top) + 72px); bottom: auto }`); further toasts queue (FIFO, at most
10; older queued toasts are dropped and counted in the log). The same text within 10 s is
coalesced into the visible toast with a counter "x{n}". Every toast has a close button;
`warn` and `error` toasts use `role="alert"` on their text, others inherit `#toast`
`role="status"`. Recoverable `E-*` reports are toasted at most once per code per 10 s
(Part 4.9).

#### 7.11.5 Multiplayer privacy statement (S-NET-01)

```text
What is shared
When you connect, Finger Lickin Music sends the other players: your display name, your
character's appearance, your ready state, the buttons you press during a song with their
timing, and your scores. The host also sends the room state, the song choice and the
results. Nothing else is sent: no files, projects, recordings, settings or history.
Connections go directly between the devices. Invite and answer codes contain your
device's network addresses, so share them only with the people you play with.
Nothing is stored on any server.
```

Additional lines: when the STUN option is on, "The STUN option contacts Google's public STUN
server to find network routes; it receives your network address but no game data."; in the
Online edition, "The relay server at {relayUrl} forwards these messages between players and
stores nothing." Part 10.2 restates this statement and must match it word for word.

"Limits of this version" block (Part 1.5, verbatim, plus the limits line):

```text
Limits of this version
- Instrument sounds are synthesized by this file; no sampled sound bank is included, so
  timbres approximate General MIDI instruments rather than reproduce recordings.
- Import: MIDI (.mid, .midi) format 0, 1 and 2; MusicXML (.xml, .musicxml, .mxl);
  Guitar Pro 3, 4 and 5 (.gp3, .gp4, .gp5). Guitar Pro 6 and 7 files (.gpx, .gp) cannot
  be imported. Audio files (.wav, .mp3, .ogg, .flac, where this browser can decode them)
  are imported as backing audio only; notes are never generated from audio.
- MusicXML and Guitar Pro files are imported as musical events; sheet music and
  tablature are not displayed.
- Studio effects are a master limiter and one global reverb. Per-track EQ, delay,
  compression and automation are not included.
- Multiplayer: 2 to 4 players in Synchronized Play or Cooperative Band. Shared studio
  editing, two players on one keyboard, joining a song in progress and continuing after
  the host leaves are not included.
- MIDI devices are used only where the browser offers Web MIDI on a secure page.
- Browser and file-format support is listed in docs/COMPATIBILITY.md and reflects
  recorded tests, not assumptions.
- Sound: up to 64 voices at once on desktop and 32 on mobile; at the limit, the quietest
  released notes stop first, then the oldest. Projects: up to 32 tracks, 100,000 notes per
  track and 1,000,000 events.
```
